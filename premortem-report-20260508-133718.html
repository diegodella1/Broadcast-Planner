Broadcast Planner failed 6 months from now

Premise: legacy playout manager compiled and had useful admin screens, but the team stopped trusting it for real broadcast playout. This report works backward from that failure and turns it into an improvement plan.

Generated 2026-05-08 13:37:18 7 failure modes Tests passed: 12 Build passed
Most likely failure Output reliability lags behind CMS functionality.

The app has strong scheduling direction, but renderer behavior and end-to-end playout are not yet tested or instrumented like broadcast infrastructure.

Most dangerous failure Silent wrong output reaches air.

Database failure can fall back to mock schedule, or playback can freeze/fail while the browser route still appears alive.

Hidden assumption "The app renders" means "the signal is safe."

Broadcast safety requires real data, playable media, valid schedule, and automatic recovery. Rendering alone proves too little.

Revised Plan

1. Make real data non-negotiable

  • Remove mock fallback from production data paths.
  • Show explicit data-source state in admin screens.
  • Keep demo data behind `ALLOW_DEMO_DATA=true` only.

2. Lock privileged mutations

  • Add `requireAdmin()` to service-role write routes.
  • Add static/test guard for API routes using service client.
  • Audit uploads, imports, settings, edits, and overrides.

3. Build playout-grade fallback

  • Add renderer state machine: loading, playing, stalled, errored, ended, fallback.
  • Wire video error/stall/end events to fallback.
  • Add media-start timeout and debug media state.

4. Turn readiness into enforcement

  • Add database-level overlap protection.
  • Publish only with no critical issues and ready fallback.
  • Use a pass/fail day readiness checklist, not only counts.

5. Add live operations panel

  • Show now, next, active media state, warnings.
  • Add force fallback, disable overlay, force next, hold block, clear override.
  • Store overrides and audit them.

6. Add broadcast smoke tests

  • Playwright: login, create block, publish, output route.
  • Pixel/media checks for nonblank clean output.
  • Bad media URL must trigger fallback.

Failure Modes

Severity high / likelihood medium

Silent mock fallback

Supabase fails, but `lib/data.ts` returns `mockSchedule`. Operators see a believable schedule that is not the real on-air plan.

Assumption: A working render means real data was loaded.

Warning signs: Health passes while Supabase fetches fail; output shows blocks not in production DB.

Severity high / likelihood medium

Service-role API exposure

Upload/import/settings routes write with privileged Supabase access without consistent route-level admin enforcement.

Assumption: Environment secrecy is enough protection for privileged writes.

Warning signs: `createServiceClient()` in API routes without `requireAdmin()`; storage objects with weak audit trail.

Severity high / likelihood high

Renderer not playout-grade

Video stalls, iframe autoplay fails, HLS errors, or remote media breaks. Browser output remains alive but shows black/frozen/incorrect content.

Assumption: Ready URL means successful browser playback.

Warning signs: No tests for media errors, stalls, ended events, autoplay failures, or iframe failures.

Severity medium / likelihood high

Health checks stay advisory

UI detects gaps, overlaps, and asset problems, but not every unsafe state is impossible at database/API level.

Assumption: UI health checks are enough to protect broadcast state.

Warning signs: Direct writes or future endpoints can bypass app-layer checks.

Severity medium / likelihood high

Live recovery UX too slow

Operator must navigate schedule rows and edit blocks during a live issue instead of using one-click recovery controls.

Assumption: Editing workflows are fast enough for live recovery.

Warning signs: Live incident actions require multiple page transitions.

Severity medium / likelihood medium

CMS breadth outruns reliability

Slides, Vimeo, uploads, lower thirds, and settings expand before the team proves 12-hour unattended output stability.

Assumption: Unit tests and build are enough confidence for playout.

Warning signs: Tests cover schedule logic but not browser output behavior.

Severity medium / likelihood medium

Environment drift breaks production

Wrong base URL, missing bucket, missing encryption key, bad Vimeo token, or bad Supabase key passes build but fails at runtime.

Assumption: Successful `next build` means production is ready.

Warning signs: Health route does not verify critical dependencies.

Pre-Launch Checklist

  • Production data paths never return mock schedule unless explicit demo mode is enabled.
  • Every service-role write route has admin auth and audit log.
  • Live output automatically switches to fallback when media URL fails.
  • Active day cannot publish with overlap, missing asset, unsupported asset, or missing ready fallback.
  • Playwright smoke proves login, schedule creation, publish, live output, preview output, and fallback behavior.
